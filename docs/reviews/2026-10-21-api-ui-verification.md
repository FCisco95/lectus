# Local API browser verification — 2026-10-21

## Scope

The local API settings UI was tested in headless Chromium with a synthetic Tauri bridge. Every command is mocked: no server API was enabled, no real token was read, no native clipboard write occurred, and no microphone, cloud provider, installed Lectus process or user configuration was used. These checks establish frontend behavior only; the Rust server, actual authentication/CORS, audio validation, membership enforcement and transcription require separate native receipts.

## Repeatable run

Set `UI_SMOKE_API=1`, then run `node scripts/ui-smoke.mjs`. The ordinary smoke suite remains the default when that variable is absent. The API mode writes only `docs/reviews/2026-10-21-api-ui-smoke/`.

The harness requires a resolvable Playwright package, or `PLAYWRIGHT_MODULE` pointing to an existing package. `PLAYWRIGHT_CHROMIUM_EXECUTABLE` optionally points to an existing Chromium executable. This run reused the existing npm-cache playwright-core package and Chromium headless shell 1243; no app dependencies were added. A loopback-only Vite server is started on port 4179 (override with `UI_SMOKE_PORT`) and stopped afterward.

## Behavior tested

1. API starts off. Opening the panel and changing port/origins/enablement does not fetch a token or save automatically. Explicit Save sends the exact settings, normalizes duplicate origins, and updates the endpoint from applied settings.
2. Invalid port and path-bearing origin are rejected before IPC. A rejected save preserves the user's draft. Discard restores applied settings. A successful save returning a listener error shows “Needs attention,” never “Server running,” and permits retry.
3. Reveal and Copy are explicit token reads. Hidden Copy does not expose the token in the field. Regenerate first focuses Cancel; Cancel restores the trigger and invokes nothing. Replace rotates once, hides the value, and a later Copy obtains the new synthetic token.
4. Activity events update busy state, errors and the five newest calls while preserving an unsaved port edit. Failed/completed outcomes, missing Origin, audio length and result-character count render without transcript content.
5. Eight screenshots cover settings and recent activity in light/dark at 1100×800 and 720×540. Token getters remain unused during screenshots. Root and modal-content horizontal overflow checks pass.

Machine-readable pass/fail results and timestamps are in [results.json](2026-10-21-api-ui-smoke/results.json). Runtime exceptions and unexpected unmocked commands are checked after every behavioral scenario.

## Final lifecycle regression checks

Seven behavioral scenarios and the eight screenshot checks passed after the final lifecycle change. With enabled=false, running=false and busy=true, the API panel shows "Finishing current API request" and the mocked pill window retains its pulsing API status with the corresponding accessible label. After busy=false, the panel shows Off and the pill indicator disappears. No token is fetched by either state transition. This verifies frontend event handling, not native in-flight cancellation.

## Visual inspection

The API panel retains the shell's spacing, type hierarchy, form treatment and status styling. At 720×540 the port row stacks vertically, the origin textarea fits, and activity entries wrap without horizontal clipping. Navigation and close remain available while the panel scrolls. Both completed and failed activity are readable in each theme. Tokens remain hidden in every captured image. Screenshots were captured with entrance animations disabled.

No product defect was found by the final fixture run. An intermediate run failed on the old “Listening on this computer” expectation while another worker changed the copy to “Server running on this computer”; the tests were updated to the final copy and rerun. This was a test expectation change, not an observed server failure.

One intermediate browser-page startup timed out at the harness's eight-second threshold with an empty body and no captured JavaScript exception. The initial app-load allowance was raised to twenty seconds; the final complete run passed. The cause of that isolated startup delay was not established.
